# Doc Comments

Every class method and exported function carries a JSDoc block, so someone
hovering a symbol learns what it does without opening the file. That's the one
exception to the repo's "no comments" rule: a `/** */` block directly above a
function or method is required; inline `//` comments, banners and prose inside a
body are still banned. Your job is to find every function that lacks one, write
it, and fix the ones that lie.

## Scope

In scope:

- `src/lib/**/*.ts` and the `<script>` of `src/lib/components/**/*.svelte`
  (functions a component exports)
- `src/worker/**/*.ts` (the worker process, its job handlers and queue)
- `src/hooks.server.ts`, `src/hooks.client.ts`, `src/service-worker/**` if
  present
- `scripts/**/*.ts`

Out of scope:

- Route files (`src/routes/**`: `+page*`, `+layout*`, `+server.ts`); their
  `load`/`actions`/`GET` shape is framework-defined. `*.remote.ts` files under
  `src/lib/remote/` are in scope.
- `src/lib/components/ui/**` (shadcn-svelte primitives, regenerated by the CLI)
- Generated output: `drizzle/**`, `.svelte-kit/**`, `build/**`, the better-auth
  schema `bunx auth generate` writes
- `tests/**` and any `*.test.ts`
- Table definitions in `src/lib/server/db/schema.ts` (not functions)

What needs a block:

- Every class method: public, `#private`, `static`, `get`/`set` accessors, and
  `constructor` when it does more than assign fields.
- Every `export function` and `export async function`.
- Every `export const name = (...) => ...`.
- Mixin factories and the methods of the class they return.
- Non-exported module helpers only when longer than about 15 lines or when the
  name doesn't make the behaviour obvious.

## Workflow

1. **Inventory with a script, not by eye.** A Bun script in the scratchpad using
   the TypeScript compiler API (`typescript` is a devDependency) walks the
   in-scope files, visits `MethodDeclaration`, `GetAccessor`, `SetAccessor`,
   exported `FunctionDeclaration` and exported `VariableStatement`s whose
   initializer is a function, and prints `file:line name` wherever
   `ts.getJSDocCommentsAndTags` returns nothing. Extract the `<script>` block of
   `.svelte` files first. If the caller gave a diff or file list, restrict to
   it.
2. **Read before writing.** Read the whole function and its call sites until you
   understand it. A block that paraphrases the name ("Gets the device") is worse
   than none.
3. **Write the block.** House style:

   ```ts
   /**
    * Moves a cover to `position`, then has the worker read where it ended up
    * once it stopped moving.
    *
    * @throws When the cover can't be reached or rejects the command.
    */
   ```

   - First line: one present-tense sentence on what it does and, when it isn't
     obvious, why a caller would pick it over a neighbour.
   - Side effects the signature hides: database writes, enqueued jobs, emails,
     cache mutation, transactions.
   - `@param` only when name and type don't carry the meaning; never restate the
     type in braces.
   - `@returns` only when the name and type don't make it obvious.
   - `@throws` when a caller has to handle the path.
   - Trivial one-liners get one line: `/** The member's display name. */`.
   - Plain English, no headings, no `@author`, `@since` or `@example` unless an
     example prevents misuse. No em dash.

4. **Fix stale blocks** in every file you open: `@param` names that no longer
   exist, missing ones, a summary contradicting the body.
5. **Edit comments only.** Don't rename, reformat or refactor code. A real bug
   you spot goes in `TODO.md` as one line under its size section.

## Verify

- Re-run the inventory: zero missing in scope (or in the given files).
- `bun run check` and `bunx prek run --all-files` still pass.

## Report

Candidates found, documented and stale blocks fixed, per area (`src/lib/dto`,
`src/lib/server`, `src/worker`, `scripts`, ...). List anything you skipped
because the code didn't tell you what it does, with `file:line`, rather than
guessing.
